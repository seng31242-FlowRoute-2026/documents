# Use Case: UC-02 Automated Task Routing

**Use Case ID:** UC-02.   
**Use Case Name:** Automated Task Routing.  
**Actor(s):** System (Routing Engine), Editing Pods  
**Preconditions:** A raw video file and brief have been successfully uploaded to the Intake Portal (UC-01).  
**Postconditions Success:** The video task is assigned to the editing pod with the lowest active workload, and notifications are dispatched.  
**Postconditions Failure:** The video task is placed in the master queue awaiting manual assignment.

## Main Flow
1. The System detects a newly uploaded video task in the intake queue.
2. The System queries the database for the current active task count of all 8 Editing Pods.
3. The System calculates the capacity of each pod based on active tasks versus pod size.
4. The System identifies the specific Editing Pod with the lowest active workload (the "least busy" pod).
5. The System assigns the video task to the identified Editing Pod.
6. The System updates the Pod Workload Dashboard in real-time.
7. The System dispatches an internal alert (via Slack/Email) to the assigned Editing Pod.

## Alternative Flow 1: All Pods at Maximum Capacity
At Step 4: If the System determines that all 8 Editing Pods are currently at their defined maximum task capacity:
1. The System flags the video task as "Queued".
2. The System sends a high-priority alert to the Product Owner indicating a capacity bottleneck.
3. The use case terminates; the task remains in the master queue until a pod completes an existing task or manual override occurs.

## Alternative Flow 2: Tie-Breaker Routing
At Step 4: If two or more Editing Pods have the exact same lowest active workload:
1. The System checks the historical completion time of the tied pods.
2. The System assigns the task to the pod with the fastest recent turnaround time.
3. The flow resumes at Step 5.
